# pape-api

Internal backend service for **Pape Mosque** (formerly "MYT") that fetches prayer times from the Diyanet AwqatSalah API and serves them as JSON.

## Overview

This service calls the [Diyanet AwqatSalah API](https://awqatsalah.diyanet.gov.tr) for Toronto (city ID `9118`), combines the daily prayer times with locally calculated iqamah times, and exposes the result on a single JSON endpoint.

It is not consumed by end users directly. A Vercel cron job calls this service and writes the response into a Supabase table (`prayer_cache`). The Pape Mosque website and Flutter mobile app read from that Supabase table.

## Architecture / data flow

```
Diyanet AwqatSalah API
        │  5 upstream calls (login + daily, eid, ramadan, weekly)
        ▼
   pape-api  (this service — Express, hosted on Render)
        │  GET /prayer-times
        ▼
  Vercel cron job
        │  writes response
        ▼
 Supabase table (prayer_cache)
        │  read by
        ├──► Pape Mosque website
        └──► Flutter mobile app
```

The important consequence for maintainers: **this service is one link in a longer chain, not the consumer-facing endpoint.** If the website or app shows wrong or stale prayer times, the cause may be here, in the cron job, or in Supabase. This service holds no state of its own — every request re-fetches from Diyanet (see [Known limitations](#known-limitations)).

Per request, the service makes five upstream calls: `Auth/Login`, then `PrayerTime/Daily/9118`, `PrayerTime/Eid/9118`, `PrayerTime/Ramadan/9118` and `PrayerTime/Weekly/9118`. Iqamah times (Fajr, Asr, Isha, Jumaa) are calculated locally in `lib/calculatePrayerTimes.js`, not supplied by Diyanet. The Jumaa time depends on whether `America/Toronto` is currently in DST.

## Endpoints

### `GET /`

Plain-text health check. Makes no upstream calls.

```
Prayer Times API is running.
```

### `GET /prayer-times`

Returns today's prayer times for Toronto with calculated iqamah times, Eid and Ramadan times, and any iqamah-change notices. `notices` is generated by comparing today's calculated iqamah times against tomorrow's, so it is usually empty.

## Error responses

Every failure returns a JSON body with this shape:

```json
{
  "success": false,
  "code": "ECONNRESET",
  "upstreamLabel": "Auth/Login",
  "attempts": 3,
  "status": null,
  "message": "Auth/Login failed: request to https://awqatsalah.diyanet.gov.tr/Auth/Login failed, reason: read ECONNRESET"
}
```

| Field | Meaning |
| --- | --- |
| `success` | Always `false` on an error response |
| `code` | Machine-readable cause (see table below) |
| `upstreamLabel` | Which Diyanet call failed, e.g. `Auth/Login`, `PrayerTime/Daily` |
| `attempts` | How many attempts were made before giving up (`0` if the request never left this service) |
| `status` | Upstream HTTP status if Diyanet responded, otherwise `null` |
| `message` | Human-readable description |

Status codes:

| Status | When | `code` values |
| --- | --- | --- |
| `500` | Misconfiguration or a bug in this service — not Diyanet's fault | `MISSING_CREDENTIALS`, `INTERNAL_ERROR` |
| `502` | Diyanet responded, but with an error or an unusable body | `UPSTREAM_HTTP_ERROR`, `INVALID_JSON`, `LOGIN_NO_TOKEN` |
| `504` | Connection-level failure or timeout — nothing usable came back | `ECONNRESET`, `ETIMEDOUT`, `ECONNREFUSED`, `EAI_AGAIN`, other network codes, `DEADLINE_EXCEEDED` |

The distinction is deliberate: `504` means retrying later may work, `502` means Diyanet actively rejected the request, and `500` means something on this side needs fixing. When more than one upstream call fails in the same request, the most important one is reported, in the order `PrayerTime/Daily` → `PrayerTime/Weekly` → `PrayerTime/Eid` → `PrayerTime/Ramadan`. All failures are logged regardless.

## Environment variables

| Variable | Description |
| --- | --- |
| `DIYANET_EMAIL` | Account email for the Diyanet AwqatSalah API |
| `DIYANET_PASSWORD` | Account password for the Diyanet AwqatSalah API |
| `PORT` | Port the server listens on (optional, defaults to `3000`) |

`DIYANET_EMAIL` and `DIYANET_PASSWORD` are required. If either is missing, `/prayer-times` returns `500` with code `MISSING_CREDENTIALS` and makes no upstream call.

These must be set in the hosting environment as well as locally. Render does not read the local `.env` file, so the deployed service will fail to authenticate until both variables are configured under **Service → Environment** in the Render dashboard.

## Running locally

Requires Node.js 20 or newer (the fetch layer uses `AbortSignal.any`).

```bash
npm install
cp .env.example .env    # then fill in the real credentials
npm start
```

The server listens on `http://localhost:3000` unless `PORT` is set.

```bash
curl http://localhost:3000/prayer-times
```

## Reliability notes

The Diyanet API drops connections intermittently (`read ECONNRESET`), so every upstream call goes through a shared hardened fetch helper in `lib/apiClient.js`:

- **Per-attempt timeout of 8 seconds.** `node-fetch` v3 has no `timeout` option and Node's HTTP client has no default socket timeout, so this is enforced with an explicit `AbortSignal`. Without it a stalled connection would hang indefinitely.
- **Up to 3 attempts per call**, with backoff of roughly 400 ms then 1200 ms, each with ±25% jitter.
- **Retried:** connection-level errors (`ECONNRESET`, `ETIMEDOUT`, `ECONNREFUSED`, `EAI_AGAIN` and similar), HTTP `429`, and `5xx` except `501` and `505`. A `Retry-After` header on a `429` is honoured, capped at 5 seconds.
- **Not retried:** other `4xx` responses, non-JSON bodies, and unrecognised errors — replaying these cannot help, and it avoids retrying bugs in this service.
- **25-second global deadline** across the whole request (login plus all four data calls). Its abort signal is combined with each attempt's own timeout, so in-flight requests are actually cancelled rather than left running. A retry is skipped if there is not enough time left to complete it.
- **Concurrency:** login runs first, then the four data calls run in parallel via `Promise.allSettled`. Every failure is logged, and none are left running unobserved when one of them fails first.
- **Single-flight re-login:** because the four data calls run concurrently, an expired token makes all four return `401` at once. The first one triggers a single re-login and the others wait on it, so `Auth/Login` is called once rather than four times. Each call then retries once with the refreshed token; a second `401` is a hard failure.

Retries are visible in the logs. Failed attempts are logged with `console.error`, and a call that succeeds after a prior failure logs a `console.warn`, so intermittent upstream flakiness can be observed rather than passing silently:

```
[upstream] PrayerTime/Daily attempt 1/3 failed — ECONNRESET after 179ms: ...
[upstream] PrayerTime/Daily succeeded on attempt 2/3 after 1 failure(s) (201ms)
```

## Known limitations

- **No caching or fallback.** The service holds no state between requests. If the upstream calls fail after all retries, the request fails — there is no last-known-good data to fall back to.
- **Cold starts.** Hosted on Render's free tier, so the first request after a period of inactivity may be slow while the service spins up.
- **Diyanet rate limiting.** Under heavy request volume the API starts returning `406 Not Acceptable` on data endpoints, which surfaces as a `502`. This is not retried. Normal cron traffic (once per day) does not trigger it, but repeated manual testing can.
- **Toronto only.** The city ID `9118` is hardcoded, as are the Eid iqamah times.
